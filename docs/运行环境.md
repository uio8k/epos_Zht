# 运行环境

本文档面向克隆本仓库后、从零准备运行环境的读者：安装工具链、配置 PATH、编译源码、制作硬盘镜像、启动 QEMU 运行、用 GDB 调试。文末说明 `tools/` 目录中的配套工具。

> **验证状态**：本文档的安装步骤依据 MSYS2、QEMU 官方资料与仓库 Makefile 编写，未在全新环境实测；"参考环境"一节是编写本文档时使用的课程原版环境（版本为实测值）。Unix 部分同样未实测。遇到问题请结合实际情况排查。

## 需要什么

EPOS 是 32 位 x86 的 freestanding 内核，构建与运行需要：

| 用途 | 工具 |
| --- | --- |
| 构建 shell | bash（顶层 Makefile 指定 `SHELL=/bin/bash`） |
| 编译、汇编、链接 | gcc 与 binutils（ld、as、objcopy 等），面向 32 位 i386 目标 |
| 构建编排 | GNU make |
| 还原初始硬盘镜像 | base64、bzip2 |
| 写入 FAT 分区 | mtools（mcopy） |
| 运行 | QEMU（i386 系统模拟器） |
| 调试 | GDB |

### 仓库结构

## Windows

### 1. 安装 MSYS2

1. 从 https://www.msys2.org 下载安装，默认装到 `C:\msys64`。
2. 打开"MSYS2 MSYS"终端，安装构建工具：

   ```bash
   pacman -S gcc make binutils bzip2 mtools gdb
   ```

3. 检查工具链目标：

   ```bash
   gcc -dumpmachine
   ```

   应输出 `i686-pc-msys`（32 位）。本代码固定使用 `-m32 -march=i386` 等面向 i386 的选项，如果这里输出的目标不是 32 位，构建可能失败；本文档未在新版 MSYS2 上验证过。

### 2. 安装 QEMU

1. 从 https://www.qemu.org/download/#windows 获取 Windows 版安装包，默认装到 `C:\Program Files\qemu`。
2. 顶层 Makefile 在 Windows 下调用的命令名是 `qemu-system-i386w`（对应 Makefile 中的 `W=w`），而标准安装提供的是 `qemu-system-i386.exe`。把 `qemu-system-i386.exe` 复制一份改名为 `qemu-system-i386w.exe`，与其余文件放在同一目录（运行时需要加载同目录的库文件）。

### 3. 配置 PATH

需要的两个目录：

| 目录 | 提供 |
| --- | --- |
| `C:\msys64\usr\bin` | bash、make、gcc、binutils、bzip2、gdb、mtools（pacman 都装在这里） |
| `C:\Program Files\qemu` | qemu-system-i386w（以实际安装位置为准） |

MSYS2 bash 启动时 `/usr/bin` 已在 PATH 中，只需补 QEMU：

```bash
export PATH="/c/Program Files/qemu:$PATH"
```

需要每次生效就写进 `~/.bashrc`。在仓库根目录下验证：

```bash
cd /c/path/to/epos_Zht
which make gcc objcopy mtools mcopy qemu-system-i386w gdb
```

各条都输出路径即可。

（可选）在 PowerShell 中构建时要显式配置两个目录；make 的各条命令由 MSYS bash 执行，PATH 中必须有 bash：

```powershell
$env:PATH = "C:\msys64\usr\bin;C:\Program Files\qemu;$env:PATH"
```

### 4. 构建

```bash
cd /c/path/to/epos_Zht
make
```

顶层目标：

| 命令 | 行为 |
| --- | --- |
| `make` | 只构建：-O2 编译内核与用户程序 |
| `make hd.img` | 构建并制作硬盘镜像 |
| `make qemu`（=`make run`） | 构建、制作镜像并启动 QEMU |
| `make debug`（=`make qemudbg`） | -O0 调试构建，并启动 QEMU 与 GDB |
| `make clean` | 清理构建产物与 hd.img |

构建产物：

- `kernel/eposkrnl.elf`：带符号的内核；
- `kernel/eposkrnl.bin`：Windows 下由 PE 格式内核经 objcopy 转出的裸二进制，写入镜像用的是它；
- `userapp/a.out`：用户程序；
- `kernel/kernel.ld`：由 `kernel.ld.in` 预处理生成。

### 5. 制作硬盘镜像

```bash
make hd.img
```

1. `hd.img` 不存在时，从 `hd.img.bz2.txt`（base64 编码的 bzip2 文本存档）还原出初始 FAT 镜像；
2. 用 mtools 把 `kernel/eposkrnl.bin` 以文件名 `eposkrnl`、`userapp/a.out` 以 `a.out` 写入镜像。

重复执行会直接覆盖镜像中的旧文件。内核启动后从 FAT 分区加载 `a.out` 并运行。

### 6. 运行

```bash
make qemu
```

等价于：

```
qemu-system-i386w -m 48 -boot order=c -vga std -drive format=raw,file=hd.img,index=0,media=disk
```

48 MB 内存、从硬盘（hd.img）启动、标准 VGA。该目标包含前面的构建与镜像步骤，改完代码直接 `make qemu` 即可。

### 7. 调试

```bash
make qemudbg
```

1. 以 `MODE=debug`（-O0 -ggdb）重新构建并刷新镜像；
2. 打开 GDB 窗口（Windows 下是 `start gdb -iex 'add-auto-load-safe-path .'`）；
3. QEMU 以 `-S -s` 启动：`-S` 让 CPU 启动后暂停，`-s` 在 TCP 1234 端口接受 GDB 连接。

`add-auto-load-safe-path .` 允许 GDB 自动加载当前目录的 `.gdbinit`。该文件把 GDB 连到 QEMU 并加载内核符号：

```
target remote localhost:1234
add-symbol-file kernel/eposkrnl.elf 0x100000
add-symbol-file kernel/eposkrnl.elf 0xc0100000
```

内核链接在 0xC0100000（KERNBASE 0xC0000000 + 加载地址 0x100000），物理加载地址是 0x100000；符号表按两个地址各加载一份，便于在物理地址与内核虚拟地址两种视图下解析符号。连接后执行 `continue`，系统开始运行。

## Unix（Linux / macOS）

以下内容依据 Makefile 的 Unix 分支整理，未实测。

### 准备工具

- Linux（以 Debian/Ubuntu 为例）：`sudo apt install make gcc gcc-multilib binutils mtools bzip2 qemu-system-x86 gdb`。x86_64 主机需要 gcc 的 32 位支持（gcc-multilib）；qemu-system-x86 提供 `qemu-system-i386`。
- macOS：Makefile.inc 在 Darwin 下自动给工具名加 `x86_64-elf-` 前缀，需要自行准备 x86_64-elf 交叉工具链（例如 Homebrew 的 x86_64-elf-gcc、x86_64-elf-binutils 及对应的 gdb），另需 `brew install qemu mtools`。

### 构建与运行

```bash
make hd.img
make qemu
```

与 Windows 的差异：

- 内核输出 ELF 格式（`kernel.ld.in` 的非 Windows 分支为 `elf32-i386`），链接时附加 `-Wl,-melf_i386`；写入镜像的是 `kernel/eposkrnl.elf`；
- QEMU 命令名为 `qemu-system-i386`（无 `w` 后缀）。

### 调试

```bash
make qemudbg
```

- Linux：Makefile 用 `/usr/bin/x-terminal-emulator` 打开 GDB。非 Debian 系若没有这个命令，可在另一个终端手动运行 `gdb -iex 'add-auto-load-safe-path .'`，QEMU 会在 1234 端口等待连接。
- macOS：通过 osascript 让"终端"应用打开 GDB。

## tools 工具集

`tools/` 随仓库提供，是围绕课程"扩展实现"（Intel HDA 音频驱动、钢琴 demo、串口测试）搭建的评测与调试配套。

这些脚本早期与源码树**不匹配**（路径硬编码 `epos`、依赖当时未落地的功能）；**现已对齐**：路径按本仓库布局（工作区根 + `epos_Zht/` 仓库子目录）修正、`TEST_MODE`/`TEST_SIGNAL` 构建变量落地、HDA 驱动与串口输出可用，三项验收流程实测通过（见文末"实测踩坑记录"）。

### 无人值守运行

- **`run_headless.bat [wav [out.wav [marker [watch_s]]]]`**：构建 hd.img 并无人值守启动 QEMU（`-m 48`，内存不足会起不来）；串口输出写入 `userapp/serial.log`；传 `wav` 时用 wav 后端把音频录到 `out.wav`。**注意**：QEMU 对 `-serial file:` 的输出带缓冲，外部进程通常读不到实时 marker，实际靠第 4 参数 watch 超时（默认 600s）兜底经 monitor（127.0.0.1:4444）发 `quit` 优雅退出（退出时 flush 串口与 wav 头）——短测试传 40~75 秒即可。依赖 `uv`、GNU make、`Qemu\qemu-system-i386w.exe`、mtools（在 `msys/2.0/mingw64/bin`，脚本已加入 PATH）。
- **`wait_and_quit.py <serial_log> [port] [timeout_s] [marker]`**：轮询日志文件是否出现完成标记，出现后向 monitor 端口发 `quit` 并等待 QEMU 进程退出。仅用标准库；由 `run_headless.bat` 调用。
- **`rebuild_test.bat [tempo|underrun|sine|impulse|step|sequence]`**（默认 tempo）：清 `.testmode_*` 标记与 `main.o`/`a.out`，以指定 TEST_SIGNAL 重建，并静态校验 `a.out` 内含对应字符串标记。**切换测试信号后建议用它重建**：`userapp/Makefile` 的标记机制曾因 `$(RM)` 未定义而残留旧标记、导致 `main.o` 不重建、链接出上一个信号的版本（规则已修，但此脚本是最保险路径）。
- **`prepare_song.py [src.mp3 [dst.wav]]`**：把 MP3（或 miniaudio 支持的格式）转成驱动可直接流式播放的 WAV——**单声道 44.1kHz 16-bit**（连续流只接受 16-bit；流格式只映射 44.1k/48k，故必须重采样；单声道体积减半）。用法 `uv run --no-project --with miniaudio python tools/prepare_song.py <song.mp3> samples/song.wav`；产物由顶层 Makefile 的 `samples/*.wav` 规则自动 mcopy 进 hd.img，且已 .gitignore（`samples/song*.wav`，18MB 级不入库）。宿主无需 ffmpeg（miniaudio 自带 MP3 解码）。

### 音频评测

- **`eval_audio.py`**：评测主控：构建 → 无头运行（捕获 wav 与串口日志）→ 分析（SNR/THD/clicks/xrun 等）→ 打分 → 写报告，并与基线对比。用法 `uv run --no-project --with numpy python tools/eval_audio.py [--mode test-tone|piano|both|acceptance] [--update-baseline] [--no-run]`（另有 `--full`、`--sensitivity`、`--output`、`--baseline`、`--tempo-std-max`、`--verbose`）。依赖 numpy 与 uv；得分低于阈值时退出码非零。
  - **`--mode acceptance`（驱动改造验收，三项）**：① sine 的 SNR/THD 对比 `baseline_report.json`；② `TEST_SIGNAL=tempo`（40×200ms 标准音符，用户程序打印提交间隔）的间隔标准差 ≤ `--tempo-std-max`（默认 25ms）且无 underrun；③ `TEST_SIGNAL=underrun`（音符间注入 800ms 停顿，超过 500ms 预填前瞻）须被驱动检出（计数>0）且 `[TRACE]` 日志含 UNDERRUN 事件。全部通过退出码 0 并落盘调用链日志。
- **`serial_parser.py`**：串口日志解析库，接口 `parse_serial_log(path) -> dict`；另有 `write_trace_log(parsed, path, source)` 把 `[TRACE]` 段落落盘为可读的调用链日志（原始事件流 + 按 note_id 重建的音符区间 + error 路径清单），并带命令行入口（`python tools/serial_parser.py userapp/serial.log [--out audio_trace.log]`）。正则覆盖 `hda.c`/`hda_stream.c`/`hda_trace.c` 与用户程序输出（初始化、流启停、FIFO 错误、乐谱、`[TEMPO]`/`[UNDERRUN]`、`[TRACE]`、完成标记等）。
- **`audio_metrics.py`**：音频客观指标库（仅依赖 numpy），无命令行入口：正弦拟合算频率/THD/SNR、click/pop 检测、冲激/阶跃响应、静音区、立体声平衡、xrun 检测、与源 wav 对齐比较。
- **`analyze_wav.py <file.wav> [...]`**：独立小工具，检查 wav 首/尾 5ms、50ms、200ms 的峰值/RMS/直流/最大跳变/过零率与有效音频起止。用法 `uv run --no-project --with numpy python tools/analyze_wav.py <file.wav>`。这是全套工具里唯一不依赖源码树、可直接使用的脚本。
- **`baseline_report.json` / `eval_report.json`**：评测基线与最近一次运行报告（`eval_audio.py` 默认的写入、读取位置）。

### 调试

## HDA 驱动缓冲模型（连续流，2026-10 重构）

`kernel/hda_stream.c` 采用「单调追加 + 安全余量」模型，替代早期「写指针回贴读指针」（`wrpos = rdpos`，会丢音符头部样本、缓冲退化为零深度管道）：

- **双指针语义分离**：`g_cont_data_end` = 真实数据（音符/休止符）末尾，单调递增，是 underrun 判定基准；`g_cont_wrpos` = 物理写游标，可被 `fill_ahead` 预填静音推进，写音符时回到起点——起点恒 ≥ `data_end` 且距 DMA 读位置 ≥ `HDA_CONT_MARGIN`（16384 字节 ≈ 93ms @44.1kHz 立体声），故只覆盖自写的未消费静音，不干扰正在播的数据。
- **节拍**：音符严格追加、首尾相接；`play_note` 等到「本音符剩余 MARGIN 以内」返回，用户程序耗时 ≤ MARGIN 时音符间几乎无缝 → 节拍 = 音符时值（实测 std 3.0ms / mean 201ms @200ms 音符）。休止符是显式追加的真实静音（有节拍语义），与兜底预填静音区分。
- **underrun 语义**：QEMU 3.1 对数据不足**不置 FIFOE、不停流、不通知**，BDL 回绕重复旧数据。驱动自行检测 `rdpos >= data_end`（DMA 越过真实数据末尾）→ 计数（syscall 197 `sys_audio_get_underruns`）+ 记 trace + 从 `rdpos + MARGIN` 重对齐；越界区间由 `fill_ahead` 预填的静音覆盖，听感是静音而非重复旧数据。
- **等待机制**：BCIS 中断优先（BDL 128×4KB 全条目 IOC；ISR 只做清 BCIS / 刷新读位置 / `wake_up`，不睡眠不打印）；注册失败或链路停摆自动退化为**有界自旋轮询**（周期读 LPIB 让 MMIO 锚定 QEMU 定时器 + 每 64 轮 `sys_task_yield`）。当前捆绑 QEMU 配置下 e1000 与 HDA 同为 IRQ 11 且本内核向量表无共享链，注册保护判空后走轮询。
- **调用链日志**（`kernel/hda_trace.c`，新增）：64KB 环形缓冲、定长条目（`struct hda_trace_rec` 24 字节，容量按 `sizeof` 推导 = 2730 条；PIT 时基 + 事件类型 + note_id + 字节区间 + 指针快照），播放热路径零串口输出（吸取逐音 printk 拖慢播放的教训）；`sys_audio_stop` 结束时批量 dump `[TRACE]` 段落，dump 逐条关中断拷贝避免与 ISR 追加撕裂；`serial_parser.write_trace_log()` 落盘 `tools/audio_trace.log`。

### 整曲流式播放（`sys_audio_play_file_stream_ms`，syscall 198）

- **背景**：整曲 WAV（单声道 44.1kHz 16-bit，220s ≈ 18.5MB）远超内核堆（12MB），不能像采样那样整块载入，需要从 FAT 分块读盘、边读边播。宿主用 `tools/prepare_song.py` 把 MP3 转成该格式（见"无人值守运行"节）。
- **实现**（`kernel/hda_audio.c` + `kernel/hda_stream.c`）：解析 WAV 头后循环「读 256KB → `hda_cont_append` 追加进连续流」（内部编号 + trace + 驱动侧 Q8 增益），内存占用恒定（读缓冲 256KB，与文件长度无关）；收尾 `hda_cont_drain` 后由 `audio_stop()` 追尾部静音并停流。环形缓冲按用途分配：流式 4MB（256×16KB BDL）、音符/休止符 512KB（128×4KB BDL）；写入位置与 LPIB 之间保持可配置安全余量（`hda_cont_reserve(..., safety)`）。
- **默认演示**（`userapp/main.c`，`#else` 分支）：整曲播放 `song.wav`（Enya - We Wish You a Merry Christmas）；旧的「VGA 希尔排序 + 钢琴」演示完整保留，用 `make SORT_DEMO=1` 构建（或 `tools/rebuild_test.bat` 之外直接 `make -C userapp run SORT_DEMO=1`）。
- **实测（整曲 220s，2026-10-14）**：`underruns=0`；录音与源 PCM 逐段（每 20s）相关性全部 1.00000、0 段偏差、结尾完整（末尾 25s 相关 1.0000）。为什么流式缓冲要 4MB 见踩坑表「LPIB 推进快于实际消费」一行。

## 实测踩坑记录（2026-10-14 驱动重构）

| 现象 | 根因 | 处置 |
|---|---|---|
| 切换 TEST_SIGNAL 后 a.out 仍是旧信号 | `userapp/Makefile` 标记规则用了本环境未定义的 `$(RM)`，展开为空命令被 `-` 吞掉，旧 `.testmode_*` 残留 → `main.o` 不重建 | 规则改 `-rm -f .testmode_*`；并用 `rebuild_test.bat` 重建验证 |
| watcher 空等 600s | QEMU `-serial file:` 输出带缓冲，外部进程读不到实时 marker | `run_headless.bat` 第 4 参数化超时，短测试传 40~75s |
| 每个音符都报 underrun | 判定条件误用「安全余量不足」（而 finish 的退出条件恰好让余量逼近 MARGIN） | 判定改为 `rdpos >= data_end`（DMA 越过真实数据末尾） |
